# TurnoutId, PositionReporter, DigitalOutput Migration & Turnout Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement Build Order step 8 in `docs/software-class-list.md` — `Turnout`, the thin composition class that wires config/output/sensor/motion together and reports position changes. It needs `TurnoutId` and `PositionReporter` (neither built yet), and it's the first class to actually call `DigitalOutput`, which forces that port's overdue migration from `set(bool)` to `write(Level)` (flagged as scaffolding debt since the very first doc sync).

**Architecture:** `TurnoutId` is a small value-object wrapper (same style as `Duration`/`Instant`). `PositionReporter` is a new driven-side port, with a hand-written `FakePositionReporter` test double (this repo's established `Fake*` naming, same divergence already accepted for `Clock`/`DigitalOutput`/`DigitalInput` — the doc calls it `CapturingReporter`). `DigitalOutput`/`FakeDigitalOutput` are migrated in place, mirroring exactly how `Clock`/`FakeClock` were migrated when `Debouncer` first needed `Instant`. `Turnout` composes already-built collaborators via dependency injection (`DigitalOutput&`, a `FeedbackSensor`, a `TurnoutMotion`, `PositionReporter&`) rather than holding a full `TurnoutConfig` — see the Global Constraints note below for why.

**Tech Stack:** PlatformIO `native` environment, C++17 (`std::optional`), Catch2 3.7.1 (vendored, `test_framework = custom`).

## Global Constraints

- Domain code must compile and run under the `native` PlatformIO environment **without** `Arduino.h`. (`CLAUDE.md`)
- No mocking framework — hand-written fakes only (`FakeDigitalOutput`, `FakePositionReporter`, reusing already-merged `FakeDigitalInput`). (`CLAUDE.md`)
- TDD throughout: failing native test first — actually run it and see it fail — then minimal implementation, then green. Do not write test and implementation together. (`CLAUDE.md`)
- Classes are built needs-driven, not speculatively. (`CLAUDE.md`) **This plan deliberately does NOT build `TurnoutConfig` or `GpioPinId`,** even though `docs/software-class-list.md` says `Turnout` "composes config, output, sensor and motion." Tracing through what `Turnout` actually *does* with a config: `id()` needs a `TurnoutId`; the "output pin"/"feedback pin" fields are consumed only by the composition root (to wire up ESP32 adapters, Build Order step 11 — not started) and by `NodeConfig::validate()` (Build Order's Node Configuration & Commissioning work — not started). Nothing in `Turnout`'s own logic needs a pin number, since `DigitalOutput&`/the `FeedbackSensor`'s `DigitalInput&` are already pin-agnostic port references injected by the caller. Building `TurnoutConfig`/`GpioPinId` now, with no consumer, would be speculative. `Turnout`'s constructor takes the pieces it actually uses directly: `TurnoutId`, `DigitalOutput&`, an `Orientation` (for the write path — see below), an already-built `FeedbackSensor`, an already-built `TurnoutMotion`, and `PositionReporter&`.
- **Why `Turnout` takes its own `Orientation`, separate from the one already inside its `FeedbackSensor`:** the same physical wiring convention applies to both reading feedback and driving the output (one relay circuit, one electrical sense), so the caller passes the same `Orientation` value to both `FeedbackSensor`'s constructor and `Turnout`'s constructor. `Orientation` is a small, cheap-to-copy value type, so this is not wasteful — it's two independent facts that happen to share a value, not shared mutable state.
- **`Turnout`'s reporting design decision (this plan's, not a literal doc quote beyond "reports on change"):** `Turnout` tracks `std::optional<TurnoutState> lastReportedState_`, starting empty. `tick()` reports whenever `motion_.state()` differs from `lastReportedState_` **or** `lastReportedState_` has never been set — this means the very first `tick()` after construction always reports (announcing the starting state), which matches the adapters section's rationale for the retain flag ("if the node publishes before JMRI connects, an unretained message is lost and JMRI sits on a stale assumption" — the system needs to publish an initial state, not just changes). `moveTo()` itself never reports directly; the next `tick()` naturally picks up whatever state `moveTo()`'s `commandTo()` produced.
- Migrating `DigitalOutput`: before changing it, grep the repo for other consumers of `DigitalOutput::set()`/`FakeDigitalOutput::isSet()`/`setCallCount()` beyond the files this plan touches — same safety check the `Clock` migration did. If Task 2 finds one, stop and report it rather than silently breaking it.
- `native`'s `build_flags` includes `-Ilib/McsCore/src` — use include paths like `"domain/TurnoutId.h"`, matching existing files.
- Commits in this repo must go through the `/arlo-commits` skill (CLAUDE.md) — never hand-written `git commit`. ACN's "Small Features and Bug Fixes" rule caps any `F`/`B` commit that changes more than 8 lines of code (including tests) at risk level `!` — it cannot be `.`/`^` regardless of test coverage. Task 2 (migration) is a refactor (`r`), not `F`/`B` — judge its risk against the refactor ladder instead (see `references/acn-notation.md` in the `arlo-commits` skill), same as the `Clock` migration. Tasks 1, 3, and 4 are new `F` behavior well over 8 lines, so expect `! F` for those.
- Every step that changes files ends with `pio test -e native` passing before moving on.

class TurnoutId

```cpp
#pragma once

#include <optional>
#include <utility>

#include "domain/TurnoutId.h"
#include "domain/TurnoutPosition.h"
#include "domain/TurnoutState.h"
#include "domain/TurnoutMotion.h"
#include "domain/FeedbackSensor.h"
#include "domain/Orientation.h"
#include "domain/Instant.h"
#include "ports/DigitalOutput.h"
#include "ports/PositionReporter.h"

class Turnout
{
public:
    Turnout(TurnoutId id,
            DigitalOutput& output,
            Orientation orientation,
            FeedbackSensor sensor,
            TurnoutMotion motion,
            PositionReporter& reporter)
        : id_(id),
          output_(output),
          orientation_(orientation),
          sensor_(std::move(sensor)),
          motion_(std::move(motion)),
          reporter_(reporter)
    {
    }

    void moveTo(TurnoutPosition position, Instant now)
    {
        output_.write(orientation_.toLevel(position));
        motion_.commandTo(position, now);
    }

    void tick(Instant now)
    {
        sensor_.sample(now);
        motion_.update(sensor_.observed(), now);

        TurnoutState current = motion_.state();
        if (!lastReportedState_.has_value() || *lastReportedState_ != current)
        {
            reporter_.report(id_, current);
            lastReportedState_ = current;
        }
    }

    TurnoutId id() const
    {
        return id_;
    }

private:
    TurnoutId id_;
    DigitalOutput& output_;
    Orientation orientation_;
    FeedbackSensor sensor_;
    TurnoutMotion motion_;
    PositionReporter& reporter_;
    std::optional<TurnoutState> lastReportedState_;
};
```
